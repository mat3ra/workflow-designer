Workflow Designer UX Pass

The same exercise we ran for Materials Designer, applied to the workflow designer: what the UI does today, where it works against the user, and quick mockups of what to introduce. Findings come from running the standalone demo (npm run dev, all 55 standata workflows) and reading the component tree in this repo, @mat3ra/wove, and @mat3ra/ave.

The one-sentence diagnosis: the designer shows the same information two or three times, hides the two most common actions (edit a unit, add a unit) behind tiny targets and dropdowns, and spends its pixels on UUIDs and empty canvas instead of the workflow itself.

Reviewed 2026-08-15 Source: standalone demo @ src/standalone Screens: 16 captured states
01

How it looks today

Four representative states, captured from the running app with the Band Structure + Density of States and K-point Convergence workflows on silicon.

Issue inventory

  • W1The left panel duplicates the right panel. Subworkflow cards repeat the property chips, application line, and full unit list that the right panel already shows — one third of the screen spent on a second copy, and it’s unclear which copy to act on.high
  • W2Flowchart nodes are illegible at default zoom. Auto-fit shrinks unit cards to ~110 px; names render around 6 px. Any workflow past ~5 units (K-point Convergence has 10 plus a branch) cannot be read, while the canvas stays mostly empty.high
  • W3Raw UUIDs everywhere. Under every subworkflow card, under every unit row, on every flowchart node, and as a disabled “FlowchartId” field placed beside the first input of the unit dialog. No user task needs them.high
  • W4Editing a unit is a four-step archaeology dig. Find the ~16 px pencil on a tiny node → modal (“Unit settings”, doesn’t say which unit) → expand the Details accordion → switch sub-tabs. Side rail buttons are icon-only with no tooltips.high
  • W5Important Settings forms lack labels, units, and state. Bare inputs under a shared description; faint grey section headers; no indication of edited-vs-default, no reset, no search. This is the tab scientists touch most.high
  • W6Compute tab is an unlabeled checkbox. No text explains that it enables a per-subworkflow compute override, or what the defaults are.med
  • W7Destructive actions are instant. Trash icons on cards and nodes delete immediately — no confirmation, no undo toast, no undo/redo stack anywhere in the designer.med
  • W8Add flows are hidden and hostile. Adding a unit lives behind “Select Unit Actions ▾ → Add Unit”. Adding a subworkflow means the header kebab → “Add subworkflow”, or “Paste subworkflow” — a raw JSON textarea. No searchable library, no insert-in-place on the canvas.med
  • W9Tab scope is ambiguous, names vague. Overview / Important settings / Detailed view / Compute look like page tabs but apply to one subworkflow; “Detailed view” mostly repeats Overview’s chips; Overview stacks the Details accordion above the flowchart, pushing it below the fold.med
  • W10Job-runtime chrome leaks into design mode. Every card wears an “idle” status chip while you are designing — status belongs to jobs, not templates.low
  • W11Names repeat; property chips duplicate. The workflow name appears 3–4 times per screen; property chips show snake_case keys and duplicates (fermi_energy twice for Band Structure + DoS).low
  • W12Hard-coded legacy light theme. WorkflowDefaultLayout pins the old light MUI theme, so the designer clashes with any host theme (the standalone demo renders a light island in a dark page) and can’t follow the platform’s design refresh.low
02

Direction

One principle fixes most of the inventory: one canvas, one source of truth, selection drives an inspector. Subworkflows become a compact step rail (they are a sequence, not a diagram). The canvas gets the reclaimed width and renders units at readable size. Everything about the current selection — subworkflow or unit — edits in a right-hand inspector instead of modals and duplicated panels. UUIDs, status chips, and the second copy of every list simply go away.

The five mockups below are quick, not pixel-final — enough to agree on structure before touching wove.

Where the changes live & suggested order

The designer is a composition of packages, so the mockups split cleanly: @mat3ra/wove owns the flowchart canvas and node cards; this repo owns the shell, tabs, and panel composition; @mat3ra/wode owns the settings schemas/uiSchemas; @mat3ra/ave owns the execution-unit editor internals; the webapp injects header components.

Phase 1 · days

Quick wins

The table above, mostly cosmetic + safety. Immediately felt, zero structural risk.

  • UUID removal, labels, tooltips
  • Delete confirm / undo, dirty dot
  • Tab renames, node size clamp
Phase 2 · 1–2 sprints

Settings & editing depth

Highest-value redesigns inside the current layout.

  • Important Settings rebuild (Mockup B)
  • Input editor + variables panel (Mockup D)
  • Compute form (Mockup E)
Phase 3 · 2–3 sprints

Shell relayout

The structural move once 1–2 have de-risked the parts.

  • Rail · canvas · inspector (Mockup A)
  • Edge insert + palette + step library (Mockup C)
  • Theme tokens instead of the pinned legacy theme
